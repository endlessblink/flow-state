# Canonical Writer Matrix

This document is the source inventory for **TASK-1944**. It maps the current
production mutation seams that must move behind the signed-user canonical
operation, revision, receipt, and change-sequence boundary.

The VPS Supabase database is the intended production source of truth. Today,
however, most callers write tables directly and infer success from a successful
PostgREST response, a drained local queue entry, a Realtime event, or an in-memory
projection. None of those alone proves that the same operation can be replayed,
read back, or observed by another surface at a known canonical revision.

## Contract terms

- **Operation identity** is created at user intent and survives queuing,
  coalescing, retries, process restarts, and transport loss.
- **Canonical proof** is a durable receipt containing the operation identity,
  scope, entity and action, canonical row revision, global change sequence,
  replay status, committed timestamp, and read-back projection/hash.
- **Projection** means Pinia, localStorage, IndexedDB/Dexie, Electron state, a
  service-worker cache, or a sidecar snapshot. Projections may be optimistic or
  offline-capable, but are never canonical proof.
- **Change catch-up** is an RLS-scoped, paginated `changes-after-sequence` read.
  Realtime and Electron IPC are fast invalidation paths, not correctness paths.
- **Legacy capture** means compatibility triggers assign row revisions and append
  change events to direct writes until the corresponding writer cohort migrates.

## Dependency-ordered migration waves

| Wave | Target command cohort | Entry condition | Exit condition |
| --- | --- | --- | --- |
| **W0 — capture** | Operation ledger, row revisions, tombstones, compatibility triggers, change ledger, receipt lookup, and `changes-after-sequence` | Redacted schema/RLS inventory is complete | Every listed legacy writer produces a revision and change event; no existing caller has been cut over yet |
| **W1 — task core** | `task.create`, `task.patch`, `task.softDelete`, `task.restore`, `task.permanentDelete`, and receipt lookup/replay | W0 triggers are active | Renderer, offline replay, Electron sidecar, and Local API use the same task commands; no task command reports committed without a receipt |
| **W2 — task document** | `task.doneForNow`, `task.merge`, `task.subtasks.apply`, `task.instances.apply`, recurrence-chain delete/stop, and schedule transforms | W1 task revision/CAS contract is stable | Embedded arrays and recurrence state change atomically against one base task revision; completed subtasks are preserved unless explicitly deleted |
| **W3 — convergence** | Durable cursor/catch-up clients for web, installed PWA, Electron renderer, Local API/Hermes, and service-worker wake/reconnect | W1 receipts and W0 change reads are stable | All task surfaces converge with Realtime intentionally dropped; cursors advance only after projection persistence |
| **W4 — planning structure** | Project, group, group-geometry, lane, task-membership, and cross-entity delete commands | W3 catch-up client is reusable | Project/group/lane commands return receipts; dependent task reassignment and soft-delete occur transactionally or as a receipt-linked operation set |
| **W5 — time and focus** | Timer lifecycle/leadership commands, focus-history append, and work-profile updates | W3 catch-up is reusable and timer invariants are locked | Leader/CAS behavior is preserved; stop/complete and history writes are idempotent and receipt-backed across app, sidecar, and KDE reads |
| **W6 — preferences and context** | Settings patch/replace, AI work profile, task/project context, memory event, belief, edge, feedback, and snapshot commands | W3 catch-up is reusable | Device-local secrets remain local; synchronized settings/context mutations have operation identity, receipt, revision, and catch-up |
| **W7 — adjacent producers** | Quick sort, comments, notifications, push subscriptions, workspaces/members/invites/activity, AI conversations, WhatsApp task intake, Storage/image lifecycle, and admin/restore scripts | The owning entity cohort above is stable | Every remaining production writer is either on a command cohort or explicitly documented as device-local/administrative with an audited compatibility path |

W0 must precede every writer cutover. W3 may begin as soon as W1 exists, but it
does not make W2 or later cohorts canonical by itself. W4 through W6 may ship
one entity family at a time as long as compatibility capture remains installed.

## Cutover rules

1. Install and verify W0 compatibility capture before changing any caller.
2. Lock the current domain invariant with a contract test before replacing its
   writer. A generic table adapter must not become the place where task,
   recurrence, timer, or geometry rules are reimplemented.
3. Migrate one complete command path at a time: intent creation, durable queue,
   server command, receipt persistence, projection update, Realtime hint, and
   cursor catch-up.
4. During compatibility, a legacy direct write receives a canonical revision and
   change event with `source=legacy`; it must not receive a fabricated successful
   operation receipt.
5. Do not delete a direct fallback until adoption telemetry/status proves the
   corresponding command works for web, PWA, Electron, Local API, offline replay,
   personal and workspace scopes, and response-loss retry.
6. Coalescing may reduce network calls but must retain a durable mapping from
   every child operation to its outcome/receipt.
7. A caller may show `pending`, `queued`, `conflict`, or `canonical`. It may show
   `committed` only after validating and persisting the canonical receipt.
8. Production deployment and mutation fixtures remain separately approval-gated;
   repository tests and local disposable fixtures do not prove live adoption.
